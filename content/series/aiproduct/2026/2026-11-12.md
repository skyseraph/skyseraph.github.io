## 需求雷达

### 需求 1：agent 代客交易的「委托凭证」断层

**痛点**：来自今日 [United 封禁](https://www.cbsnews.com/news/united-airlines-bans-ai-agents-booking-flights/)与 [Southwest 反向开放](https://www.cbsnews.com/news/united-airlines-bans-ai-agents-booking-flights/)——agent 只能持用户密码行动，供给方只能在「全封」与「进 ChatGPT 渠道」之间二选一；OpenAI 品牌认领（上期）也只是平台单边方案。**场景**：一位旅客的 agent 每月代订 3 次机票——航司要的是每单可归因、限额、可撤销、出事可追偿的身份凭证，而不是一个登录态。**机会**：中立方的委托授权协议（细粒度 scope + 交易限额 + 审计流水），先切旅行与电商比价下单这两个封禁压力最大的垂直；买方是供给方（航司/零售的欺诈与渠道团队），不是 agent 厂商——这是与现有「agent 记忆/编排」赛道的差异。

## 产品创意

### 创意 1：Entrée — agent 的可验证委托凭证

- **MVP**（8 周）：做「OAuth for agent 交易」的最小环：用户签发带限额与scope 的短期凭证 → agent 持凭证调用 → 商户侧 SDK 验签并留审计流水。只做航司 OTA 一个场景打通全链路，明确不做支付清算、不做 agent 本体。
- **定价锚点**：按验证调用计费，对标供给方的欺诈拒付与 bot 滥用成本（United 们已经在付这笔钱），不对标 password manager 的订阅价——那是 C 端心智，卖不动 B 端。

### 创意 2：Fastpath — agent 网关的决策快车道

- **MVP**（6 周）：基于 Decisions API 类原语（choice/noul 一次前向）重构 agent 网关中的路由、风控、内容分级三类高频判断，承诺 token 成本降 60% 以上、延迟进 250ms；只做判定型流量改道，不做生成与编排。
- **定价锚点**：按节省 token 分成，对标客户现有生成 API 账单（可算出来的差价），不对标 APM/可观测性工具的按主机计费——省的钱在账单上，报价就该长在账单上。
